Recorded native emergency read, real failure message and later glyph creation

The glyph tracker count can go below zero

A dying low-level Warrior reads an unknown scroll while standing on a doorway. The scroll is a Rune of Protection; a doorway cannot hold one, and the game really reports that there is no clear floor. The Borg handler for that message removes a glyph that was never tracked, so the count becomes -1. The next time the Borg commands a rune creation, the guarded writer stores the position at index -1: four bytes in front of the two tracking arrays.

What the controls establish

The same emergency read on ordinary floor creates the rune with no failure message; the logs are byte-identical before and after the correction. An ordinary tracked creation from a known scroll also stays identical. Only the failed read changes: the corrected handler leaves an empty tracker empty, and the later creation is stored at index 0.

Memory error evidence

Under AddressSanitizer the original aborts inside the glyph creation choice in borg-fight-defend.c with a heap-buffer-overflow WRITE before the array of size 4 at offset -4 bytes before a tracking array; the corrected build runs the same scenario cleanly. Without the sanitizer the same run is observable through the tracker count: -1 after the message and 0 after the creation instead of 0 and 1.

Experiment conditions and limits

Native Human Warrior level 1, depth 5, seed 1000, wounded to 8 HP, lit constructed arena, one awake mage summoner adjacent, a torch with fuel, one unidentified Rune of Protection scroll; a second, identified one is carried after the emergency read (flavor awareness is per kind). The production caution and defense routines choose; the actual requested inventory letters are validated and the reads execute through the native scroll command. The failure message is produced by the game and parsed through the real terminal scrape path.

This isolates the tracker count transition and the guarded creation write, not full autonomous play, monster AI casting or world timing. No crash claim is made for every configuration; the sanitizer abort is the recorded memory error.
